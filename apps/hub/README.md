# `partycod` — сервис хаба

Координационный хаб PartyCo: база участников, аутентификация по почте и паролю, приглашения и
проекты. Первая настоящая вертикаль — не фикстуры.

**Ноль зависимостей.** Только `node:http`, `node:crypto` и `node:sqlite` — всё встроено в Node 24.
Это самохостимая коробка: каждый пакет в `dependencies` — то, что владельцу придётся обновлять и
чинить на своём VPS в три часа ночи. Здесь их нет и не должно появиться.

---

## Требования

- **Node 24 или новее.** `node:sqlite` появился встроенным и работает без флага; на Node 22 сервис
  не запустится. Проверить: `node -e "require('node:sqlite')"` — молча, значит всё в порядке.
- Ничего больше. Ни компилятора, ни `sqlite3` в системе, ни `npm install`.

## Запуск локально

```bash
node apps/hub/src/cli.js
```

Поднимется на `http://127.0.0.1:7717`, база создастся рядом с процессом в `./hub.db`.
Схема накатывается сама при старте.

Проверить, что живой:

```bash
curl -s http://127.0.0.1:7717/v1/health
# {"name":"partycod","version":"0.0.0","protocol":1,"members":0}
```

Зарегистрироваться (первый зарегистрировавшийся становится `owner`):

```bash
curl -s -X POST http://127.0.0.1:7717/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"ann@example.com","password":"correct horse battery staple","displayName":"Аня"}'
```

В ответе — `token`. Дальше он ходит в заголовке:

```bash
curl -s http://127.0.0.1:7717/v1/auth/me -H "Authorization: Bearer $TOKEN"
```

## Переменные окружения

| Переменная               | По умолчанию      | Что делает |
|--------------------------|-------------------|------------|
| `PARTYCOD_DB`            | `./hub.db`        | Путь к файлу базы. Каталог должен существовать и быть доступен на запись. |
| `PARTYCOD_PORT`          | `7717`            | Порт. `0` — свободный порт от системы (для тестов). |
| `PARTYCOD_HOST`          | `127.0.0.1`       | Слушать только петлю. Значение `0.0.0.0` открывает все интерфейсы — см. предупреждение ниже. |
| `PARTYCOD_ORIGINS`       | *(см. ниже)*      | CORS: список origin через запятую. Если задан — разрешены **только** эти. |
| `PARTYCOD_TRUST_PROXY`   | выключено         | `1` — брать IP клиента из `X-Forwarded-For`. Включать **только** за своим реверс-прокси. |
| `PARTYCOD_RATE_LIMIT`    | `10`              | Попыток входа/регистрации/`peek` с одного IP за окно. |
| `PARTYCOD_RATE_WINDOW_MS`| `60000`           | Длина окна rate-limit'а. |
| `PARTYCOD_PUBLIC_URL`    | адрес сокета      | Основа ссылки-приглашения: `<PUBLIC_URL>/join/HTAK-4K7M-9ZQD`. |
| `PARTYCOD_SMTP_URL`      | не задано         | Только признак «почта настроена». Хаб писем **не шлёт** — см. ниже. |

**`PARTYCOD_PROJECT_NAME` больше нет.** Она существовала, пока не было таблицы `project`: имя
проекта в ответе `GET /v1/invites/peek` бралось из одной строки на всю установку — правды в ней
было ровно столько, сколько на хабе с единственным проектом, и проверить её было нечем. Теперь имя
берётся из проекта, к которому приглашение выписано (миграция 4). Если переменная осталась в
`/etc/partycod.env`, её можно убрать: сервис её не читает.

**`PARTYCOD_PUBLIC_URL` стоит задать сразу.** Без него ссылка собирается из адреса, на котором
сервис слушает, — то есть `http://127.0.0.1:7717/join/…`. Это правда и снаружи бесполезно; врать
правдоподобным доменом хуже, чем отдать бесполезную правду. `/join` обслуживает не хаб, а
десктопное приложение: хаб только знает, какой адрес подставить.

**CORS по умолчанию.** Если `PARTYCOD_ORIGINS` не задан, разрешён `http://localhost:5273` и вообще
любой петлевой origin с любым портом (`http://localhost:*`, `http://127.0.0.1:*`, `http://[::1]:*`).
Так сделано потому, что дев-превью renderer'а поднимается на случайном порту, и прибитый гвоздями
один порт ломал бы `npm run dev` со второго запуска. На петле это безопасно — там уже своя машина.
Как только `PARTYCOD_ORIGINS` задан, петлевое правило выключается целиком: хаб на VPS не должен быть
читаем чьим-то локальным localhost.

## HTTP API

Версия протокола — `1`. Все ответы — JSON, ошибки всегда одной формы:
`{ "error": { "code": "...", "message": "..." } }`. `message` — по-русски и для человека;
имён таблиц и стектрейсов в нём нет никогда.

| Метод и путь | Тело | Ответ |
|---|---|---|
| `GET /v1/health` | — | `200 { name, version, protocol, members }` |
| `POST /v1/auth/register` | `{ email, password, displayName?, inviteCode? }` | `201 { token, expiresAt, member }` · `409 email_taken` · `400 invalid_email` / `invalid_password` / `invalid_code` / `invite_invalid` |
| `POST /v1/auth/login` | `{ email, password }` | `200 { token, expiresAt, member }` · `401 invalid_credentials` |
| `GET /v1/auth/me` | Bearer | `200 { member }` · `401 unauthorized` |
| `POST /v1/auth/logout` | Bearer | `204` · `401 unauthorized` |
| `GET /v1/members` | Bearer | `200 { members }` · `401 unauthorized` |
| `POST /v1/invites` | Bearer · `{ role, email?, lifetime?, seats?, projectId? }` | `201 { invite, joinUrl, mailSent, mailPending }` · `403 forbidden` · `404 project_not_found` · `400 invalid_role` / `invalid_lifetime` / `invalid_seats` / `invalid_email` / `invalid_project` |
| `GET /v1/invites` | Bearer | `200 { invites }` · `401 unauthorized` |
| `POST /v1/invites/revoke` | Bearer · `{ code }` | `200 { invite }` · `403 forbidden` · `404 invite_not_found` · `400 invalid_code` |
| `POST /v1/invites/redeem` | Bearer · `{ code }` | `200 { member, invite, alreadyRedeemed }` · `400 invalid_code` / `invite_invalid` |
| `GET /v1/invites/peek?code=…` | — | `200 { valid, role?, projectName? }` · `429 rate_limited` |
| `GET /v1/projects` | Bearer | `200 { projects }` · `401 unauthorized` |
| `POST /v1/projects` | Bearer · `{ name }` | `201 { project }` · `400 invalid_name` |
| `GET /v1/projects/members?projectId=…` | Bearer | `200 { project, members }` · `404 project_not_found` · `400 invalid_project` |
| `POST /v1/projects/members` | Bearer · `{ projectId, memberId, role }` | `201`/`200 { project, member, alreadyMember }` · `404 project_not_found` / `member_not_found` · `403 forbidden` · `409 role_conflict` · `400 invalid_project` / `invalid_role` / `invalid_member` |

Общие для всех: `429 rate_limited` на `/register`, `/login` и `/invites/peek`, `404 not_found`,
`405 method_not_allowed`, `413 body_too_large`, `415 unsupported_media_type`,
`400 invalid_json`, `500 internal_error`.

`member` всегда одной формы:

```json
{ "id": "...", "email": "ann@example.com", "handle": "ann", "displayName": "Аня",
  "colorSlug": "teal", "role": "owner", "createdAt": 1753574400000 }
```

`createdAt` и `expiresAt` — миллисекунды epoch. `password_hash` в ответах не появляется никогда:
JSON участника собирает единственная функция `publicMember`, поэтому это свойство держится сразу
на всех эндпоинтах, а не на каждом отдельно.

### Что решено и почему

- **Роль.** Первый зарегистрировавшийся — `owner`, все следующие — `member`. Роль и цвет
  выбираются внутри той же `BEGIN IMMEDIATE`-транзакции, что и вставка, поэтому две одновременные
  «первые» регистрации не могут обе стать owner'ом.
- **Цвет** выдаётся один раз при регистрации из палитры jewel
  (`teal, rose, violet, indigo, moss, ochre`) — берётся наименее занятый, ничья решается порядком
  палитры. **Дальше он неизменен**: на этом держится вся система «кто чем владеет с одного взгляда».
  Кода, который меняет `color_slug`, в сервисе намеренно нет.
- **Handle** выводится из части почты до `@`: нижний регистр, `[a-z0-9_-]`, тег после `+`
  отбрасывается, при коллизии — суффикс (`ann`, `ann-2`, `ann-3`).
- **Почта хранится в нижнем регистре.** `UNIQUE` в SQLite побайтовый, поэтому без нормализации
  `Ann@x.io` и `ann@x.io` были бы двумя аккаунтами.
- **Неверный пароль и несуществующая почта отвечают одинаково** — один код `invalid_credentials`,
  одинаковое тело и одинаковая работа: если участника нет, пароль всё равно сверяется с
  заведомо-ложным хешем, чтобы не отличалось время. Иначе форма входа превращается в
  перечислитель зарегистрированных почт. Заблокированный аккаунт идёт тем же путём.
- **Проверок сложности пароля нет** — это осознанное решение владельца («пока без проверок»), и оно
  касается только валидации. На хранение оно не распространяется: см. ниже.

## Приглашения

Второй человек попадает в хаб только по приглашению — либо по коду, который можно продиктовать,
либо по ссылке, отправленной на почту. И то и другое — одна и та же строка `invite.code`.

```bash
# Позвать (может хозяин хаба или мейнтейнер)
curl -s -X POST http://127.0.0.1:7717/v1/invites -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"role":"member","lifetime":"week","seats":"five"}'
# {"invite":{"code":"HTAK-4K7M-9ZQD","joinUrl":"…/join/HTAK-4K7M-9ZQD", …},
#  "joinUrl":"…","mailSent":false,"mailPending":false}

# То же, но приглашение ведёт в конкретный проект
curl -s -X POST http://127.0.0.1:7717/v1/invites -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"role":"member","seats":"five","projectId":"'"$PROJECT"'"}'

# Приглашённый проверяет код ДО того, как заводить аккаунт — сессия не нужна
curl -s 'http://127.0.0.1:7717/v1/invites/peek?code=htak-4k7m-9zqd'
# {"valid":true,"role":"member","projectName":"Atlas"}   ← имя есть, если приглашение в проект
# {"valid":true,"role":"member"}                         ← приглашение только на хаб

# И регистрируется с ним
curl -s -X POST http://127.0.0.1:7717/v1/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"dima@hightale.dev","password":"…","inviteCode":"HTAK-4K7M-9ZQD"}'
```

`role` — `maintainer`, `member` или `observer`. `lifetime` — `day` (по умолчанию), `week`,
`forever`. `seats` — `one`, `five` или `any`; по умолчанию `five`, а для приглашения на конкретную
почту — `one`.

### Приглашение в проект

`projectId` — необязательное поле. Указан: приглашение ведёт **и на хаб, и в этот проект**, роль в
проекте — та же, что в приглашении. Не указан: приглашение работает ровно как раньше — место на
хабе и больше ничего, `"projectId": null` в ответе.

- **Проект за зовущего никто не выбирает.** Даже если проект у него ровно один. Приглашение — это
  место на хабе, пока человек не сказал иначе; роль на хабе и роль в проекте — разные вещи (см.
  раздел «Проекты»), и одно нажатие не должно молча раздавать обе. Клиент, который `projectId` не
  шлёт, получает то же поведение, что до миграции 4, — сегодня десктоп именно такой.
- **Позвать можно только в тот проект, куда сам можешь добавлять людей** — то есть где ты владелец
  или мейнтейнер. Чужой проект — `404 project_not_found`, неотличимый от несуществующего; свой, но
  где ты просто участник, — `403 forbidden`. Иначе приглашение стало бы обходом
  `POST /v1/projects/members`.
- **Погашение атомарно.** Место, запись в журнал и строка в `project_member` пишутся одной
  транзакцией — и при регистрации по коду, и при `POST /v1/invites/redeem`. Человек либо и на хабе,
  и в проекте, либо нигде: обещали проект, а выдали пустое приложение — это хуже, чем отказ.
- **Кто уже в проекте, остаётся с той ролью, которая у него есть.** Погашение в проект принимает,
  но не переназначает: сменить роль в проекте нельзя ни одной ручкой (`POST /v1/projects/members`
  отвечает на это `409`), и код, погашенный по ошибке, не должен быть обходным путём.

### Что решено и почему

- **`owner` не раздаётся.** Хозяин хаба один, им становится первый зарегистрировавшийся, и кода,
  который передаёт эту роль, в сервисе нет. Поэтому `owner` запрещён и в ручке, и в `CHECK`
  таблицы: обещание, которого сервис не выполняет, нельзя было бы предложить даже в выпадающем
  списке.
- **Алфавит кода — 31 знак: `ABCDEFGHJKMNPQRSTUVWXYZ23456789`.** Ни `O`, ни `0`, ни `I`, ни `L`,
  ни `1` — код должен переживать чтение вслух с первого раза. Формат `XXXX-XXXX-XXXX`.
  Та же строка продублирована в `packages/ui/src/components/AppShell/model.ts`
  (`INVITE_CODE_ALPHABET`); копии сверяет тест, который читает тот файл как текст, — иначе они
  однажды разъедутся.
- **Генерация без modulo bias.** Байты 248…255 выбрасываются, а не сворачиваются: `% 31` от сырого
  байта сделал бы первые восемь знаков алфавита на ~12.5% вероятнее остальных.
- **Ввод нормализуется, но не угадывается.** Убираются дефисы и пробелы, регистр поднимается.
  «Дружелюбных» замен `0 → O` нет и не будет: **ни того, ни другого знака в алфавите нет**, так что
  подменять не на что, а угадывание молча превратило бы опечатку в чужой живой код.
- **Места считаются по журналу.** `invite_use` — кто, когда и какой код погасил; `invite.used_count`
  существует только как условие в `UPDATE`, которое делает гонку за последним местом атомарной.
  «1 из 5» читается из журнала, поэтому это не счётчик, который можно потерять.
- **Погашение происходит в той же транзакции, что и вставка участника.** Иначе восемь человек,
  пришедших одновременно по коду на пятерых, стали бы шестью участниками (тест на это есть).
- **Негодный код останавливает регистрацию.** Не «молча как обычный участник»: человек пришёл по
  обещанию, и тихо выдать ему не ту роль — хуже, чем отказать.
- **`peek` отвечает одинаково всему мёртвому.** Истёкший, отменённый, исчерпанный, несуществующий и
  просто кривой код дают ровно `{"valid":false}`. Это единственная ручка без сессии, принимающая
  угадываемый секрет, поэтому она под тем же rate-limit'ом, что `/login`, и не сортирует догадки.
  Про того, кто позвал, и про состав команды она не говорит ничего.
- **Имя проекта в `peek` — из строки самого приглашения.** Не из переменной среды и не из списка
  проектов: ручка принимает только код, поэтому спросить «а как называется вот этот проект» ей
  нельзя и перебрать проекты хаба через неё нельзя тоже. Единственное имя, до которого можно
  добраться, — имя проекта, к которому привязан **живой код, который у тебя уже есть**, а его
  владелец раскрыл ровно настолько, насколько сам раздал код. Мёртвый код молчит и об этом.
  У приглашения без проекта поля `projectName` просто нет — пустой строки или заглушки не бывает.
- **Повторное погашение ничего не тратит.** `invite_use` имеет `PRIMARY KEY(code, member_id)`, так
  что идемпотентность — свойство таблицы, а не проверка, которую можно забыть написать.
- **Погашение повышает роль и никогда не понижает.** Иначе достаточно было бы вручить мейнтейнеру
  код «только смотрит», чтобы он разжаловал себя одним нажатием. Хозяина не трогает вовсе.
- **Живой код виден не всем.** Список приглашений читает любой участник — видеть, что человека
  позвали, нормально, и адрес приглашённого в списке остаётся: панель команды в макете так и
  показывает «dima@hightale.dev · письмо ушло 10 минут назад». Скрыты только сам код и ссылка, и
  видят их хозяин и мейнтейнеры: живой код — это место в команде, и наблюдатель, прочитавший его,
  смог бы раздать права мейнтейнера. У остальных в списке на этих двух полях `null`.
- **В списке приглашений есть `projectId`, но не имя проекта.** Список читает любой участник, а имя
  чужого проекта — это ровно то, что `GET /v1/projects` показывать отказывается. Идентификатор сам
  по себе не даёт ничего: все ручки проекта отвечают постороннему `404`, так что и оракулом он не
  становится.
- **Чужие почты не отдаются.** В `GET /v1/members` участник и наблюдатель видят свой адрес и `null`
  вместо чужих. Иначе любой аккаунт на хабе — это выгрузка адресов всей команды в один запрос.

### Почта

**Хаб не отправляет писем.** SMTP-клиент — это зависимость, а их здесь нет.

- `PARTYCOD_SMTP_URL` не задан: ответ на создание приглашения — `"mailSent": false`,
  `"mailPending": false`. UI показывает ту же ссылку и подпись «отправь как удобно».
- `PARTYCOD_SMTP_URL` задан: `"mailSent": false`, `"mailPending": true` — то есть маршрут настроен,
  но отправка ещё не реализована (в `index.js` на этом месте стоит `TODO`).

`mailSent` не станет `true`, пока письмо действительно не начнёт уходить. Ответ, который врёт про
отправку, — это участник, который две недели ждёт письма.

## Проекты

Проект — то, на чём дальше держится всё остальное из §9.1: lane'ы, claim'ы, lease'ы, merge
gate. Ничего из этого ещё нет. Здесь есть ровно две вещи: у проекта есть имя и своя личность,
и в нём есть люди.

```bash
# Создать (может любой, у кого есть сессия). Создатель становится владельцем ПРОЕКТА.
curl -s -X POST http://127.0.0.1:7717/v1/projects -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"name":"Atlas"}'
# {"project":{"id":"…","name":"Atlas","slug":"atlas","createdBy":"…","createdAt":…,
#             "archivedAt":null,"role":"owner","joinedAt":…,"memberCount":1}}

# Мои проекты — только те, в которых я состою
curl -s http://127.0.0.1:7717/v1/projects -H "Authorization: Bearer $TOKEN"

# Состав проекта
curl -s "http://127.0.0.1:7717/v1/projects/members?projectId=$PROJECT" -H "Authorization: Bearer $TOKEN"

# Добавить человека (владелец или мейнтейнер ЭТОГО проекта)
curl -s -X POST http://127.0.0.1:7717/v1/projects/members -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"projectId":"…","memberId":"…","role":"maintainer"}'
```

`project` всегда одной формы; `role` и `joinedAt` в нём — **про вызывающего**, а не про проект:
эта форма доходит только до того, кто в проекте состоит. `memberCount` считается по таблице.

В составе проекта у человека два разных поля роли: `role` — роль на **хабе** (та же, что в
`GET /v1/members`), `projectRole` — роль **в этом проекте**. Четыре слова совпадают, смысл разный.

### Что решено и почему

- **Проект не создаётся сам.** Первый зарегистрировавшийся становится хозяином хаба и не получает
  никакого проекта — пусть заведёт его руками. Сущность, которая появилась, хотя её никто не
  просил, — это ровно тот мок, от которого продукт избавляется. Пустой список и объяснение честнее
  выдуманного «Мой проект».
- **Чужой проект — 404, а не 403.** Членство проверяется тем же `JOIN`'ом, который достаёт проект,
  поэтому «такого проекта нет» и «он не ваш» — буквально один путь в коде и разъехаться не могут.
  403 сообщил бы постороннему, что проект с таким id существует, и превратил бы ручку состава в
  перебиратель идентификаторов.
- **Роль на хабе — это не роль в проекте.** Мейнтейнер хаба, которого в проект не добавили, видит
  404, как и любой посторонний. Добавлять людей может владелец или мейнтейнер **этого** проекта.
- **Роль `owner` в проекте раздаёт только владелец проекта.** Мейнтейнер не может повысить себя
  (его собственная строка мешает — см. ниже про 409) и не должен обходить это, назначив владельцем
  сообщника.
- **Строка владельца пишется в той же транзакции, что и проект.** Падение между двумя вставками
  оставило бы проект, в котором никто не состоит: он невидим во всех списках (они все идут через
  тот же `JOIN`) и войти в него нельзя.
- **Повтор того же запроса ничего не меняет** — `200` и `alreadyMember: true`, время вступления не
  двигается. Клиент, потерявший ответ, просто повторяет запрос. А вот добавление того же человека с
  **другой** ролью — `409 role_conflict`: это уже другой запрос, и бодрый `200` сказал бы, что
  изменение прошло, хотя не произошло ничего. Сменить роль этой ручкой нельзя, и другой ручки для
  этого пока нет — сообщение так и говорит, вместо того чтобы отправить к средству, которого нет.
- **Slug выводится из имени** тем же приёмом, что handle из почты: нижний регистр, `[a-z0-9-]`,
  схлопнутые разделители, до 48 знаков, при коллизии — суффикс (`atlas`, `atlas-2`). Имя целиком
  нелатинское («Хайтейл») после фильтра не оставляет ничего и падает в `project`, `project-2`.
  Транслитерации здесь нет намеренно: выдуманная таблица романизации — это догадка о чужом имени,
  а поле `name` хранит оригинал нетронутым. Если команде это будет мешать — решение владельца, а не
  наше.
- **Слишком длинное имя отклоняется, а не обрезается.** Обрезанное имя — это имя, которого человек
  не выбирал, а переименовать проект пока нечем.
- **Чужие почты не отдаются и здесь.** Состав проекта скрывает адреса по роли на **хабе**, ровно как
  `GET /v1/members`. Если бы решала роль в проекте, любой завёл бы свой проект, добавил туда всю
  команду и прочитал адреса, которые другая ручка ему показывать отказывается.

## Хранение секретов

- **Пароль лежит только как хеш.** `scrypt`, случайная соль 16 байт, N=2¹⁵, r=8, p=1, формат строки
  `scrypt$N$r$p$<salt-base64>$<hash-base64>`, сравнение — `timingSafeEqual`. Параметры записаны в
  саму строку, поэтому поднять стоимость позже можно, не инвалидируя существующие записи.
  Открытым текстом пароль не пишется никуда — ни в базу, ни в лог, ни во «временной версии»:
  временные версии доживают до прода.
- **Токен сессии** — 32 случайных байта (base64url). В базе лежит **только его sha256**: утечка
  дампа даёт хеши, а не возможность войти. Срок жизни 30 дней, продлевается при использовании.
  Плейнтекст токена существует ровно один раз — в ответе на регистрацию или вход.
- **Credential'ов провайдеров моделей здесь нет и быть не может.** Хаб — плоскость координации,
  а не вывода: ключи Anthropic / OpenAI / Google никогда не покидают машину участника. Пароль от
  аккаунта в хабе — это другое, он аутентифицирует против самого хаба, поэтому его месту здесь.

## База

SQLite в режиме WAL, один писатель.

Таблицы: `member` (та самая из §9.1, расширенная тремя колонками, которые нужны аутентификации:
`email`, `password_hash`, `color_slug`), `session`, `invite`, `invite_use`, `project`,
`project_member` и `schema_version`. Остальная схема §9.1 (`device`, `boundary`, `lane`, `claim`,
`lease`, …) сюда ещё не приехала.

**Что делает миграция 2 (`invite-and-invite-use`).** Создаёт две таблицы и четыре индекса:

- `invite(code PK, role, email, created_by, created_at, expires_at, max_uses, used_count,
  revoked_at)`. `code` — в нормализованном виде (верхний регистр, без дефисов), поэтому поиск
  побайтовый независимо от того, как код набрали. `role` — `CHECK IN (maintainer, member,
  observer)`: `owner` запрещён на уровне схемы. `email IS NULL` — приглашение по коду,
  `expires_at IS NULL` — «пока не отключу», `max_uses IS NULL` — «сколько угодно».
- `invite_use(code, member_id, used_at, PRIMARY KEY(code, member_id))` — журнал погашений.
- Индексы: `invite(created_at DESC)` — список в панели команды; `invite(created_by)`;
  частичный `invite(email) WHERE email IS NOT NULL` — «позвать снова» начинается с адреса;
  `invite_use(member_id)` — «каким приглашением вошёл этот человек».

**Что делает миграция 3 (`project-and-project-member`).** Создаёт две таблицы и два индекса:

- `project(id PK, name, slug UNIQUE, created_by → member(id), created_at, archived_at)`.
  В §9.1 у `project` есть ещё дюжина колонок — `bare_repo_path`, `trunk_ref`, `policy_bundle_id`,
  пороги гейта. Каждая из них описывает подсистему, которой ещё нет, а колонка с правдоподобным
  значением по умолчанию — это ложь, которую UI покажет как факт. Они приедут вместе с тем, что их
  наполняет. `slug` в §9.1 нет и он добавлен намеренно: из него можно собрать URL или имя каталога.
  `archived_at` — единственный слот, положенный вперёд фичи: **ни одна ручка его не ставит**,
  поэтому в ответах он всегда `null`, и API об этом честно говорит.
- `project_member(project_id, member_id, role, joined_at, PRIMARY KEY(project_id, member_id))`.
  В §9.1 здесь вместо роли `caps` (json capability strings) — движка политик, который их читает,
  никто не написал; четыре именованные роли — это то, что сервис действительно умеет проверять
  сегодня, а `CHECK` — правильное место для такого правила. `caps` можно дописать рядом с `role`
  следующим шагом, когда появится, кому его читать. Пара в `PRIMARY KEY` делает «одна строка на
  человека в проекте» инвариантом базы, а не проверкой, которую можно забыть, — та же причина, по
  которой так устроен `invite_use`.
- Индексы: `project_member(member_id)` — «в каких проектах состоит этот человек»; индекс по паре
  (его создаёт сам `PRIMARY KEY`) на этот вопрос не отвечает, потому что `member_id` в нём не
  первый. Обратное направление — «кто в этом проекте» — обслуживает как раз индекс пары.
  Плюс `project(created_at)` — порядок списка.

**Что делает миграция 4 (`invite-project`).** Добавляет `invite.project_id` (`TEXT`, nullable,
`REFERENCES project(id)`) и частичный индекс `invite(project_id) WHERE project_id IS NOT NULL` —
«какие приглашения ведут в этот проект».

Колонка nullable намеренно, и сразу по трём разным причинам: приглашения, выписанные до этого шага
(чем они были — не записал никто, и придумать ответ задним числом хуже, чем не отвечать), приглашение
от того, у кого проекта ещё нет, и приглашение, автор которого не сказал, в какой из своих проектов
зовёт. `NOT NULL` потребовал бы значения по умолчанию, а значение по умолчанию здесь — это проект,
в который приглашённый не соглашался вступать. `ALTER TABLE ... ADD COLUMN` с `REFERENCES` SQLite
разрешает ровно при `DEFAULT NULL` — что тут и есть; дальше внешний ключ работает как обычный.

Версии 1–3 при этом не редактировались: шаги дописываются следом, как и положено.

**Миграции** — не «CREATE TABLE и надеемся»: в `src/db.js` лежит нумерованный список шагов, каждый
выполняется в одной транзакции вместе с записью в `schema_version`, поэтому падение посреди
миграции оставляет базу на предыдущей версии, а не на полпути. Уже вышедший шаг не редактируют —
дописывают следующий. Если файл окажется новее сборки, сервис откажется стартовать, а не полезет
угадывать.

Рядом с `hub.db` WAL создаёт `hub.db-wal` и `hub.db-shm` — это нормально.

### Бэкап

Обычный `cp` работающей базы может дать порванную копию: часть данных в этот момент лежит в
`-wal`. Правильный способ — онлайновый бэкап средствами самого SQLite, он согласован и не требует
остановки сервиса. Ни `sqlite3`, ни каких-либо пакетов для этого не нужно:

```bash
node -e "
  const { DatabaseSync, backup } = require('node:sqlite');
  const src = new DatabaseSync(process.argv[1], { readOnly: true });
  backup(src, process.argv[2]).then(() => console.log('ok'));
" /var/lib/partycod/hub.db /var/backups/partycod/hub-$(date +%F).db
```

В cron раз в сутки плюс ротация — этого для хаба на 2–10 человек достаточно. Бэкап содержит хеши
паролей и хеши токенов, то есть это чувствительный файл: права `600`, владелец — не `partyco`.

### 4. TLS — не опция

> **Сервис слушает plain HTTP и обязан стоять за TLS-терминатором.**
>
> По этому сокету ходят пароли и токены сессий открытым текстом. Хаб, выставленный в интернет
> напрямую по HTTP, отдаёт пароль каждого участника любому, кто слушает канал — от Wi-Fi в кафе до
> транзитного провайдера. TLS здесь не «хорошая практика», а условие, без которого разворачивать
> сервис наружу нельзя.
>
> Терминатор (Caddy, nginx, Traefik) ставится перед сервисом; наружу торчит только он, а 7717
> остаётся на петле или закрыт фаерволом.

Caddy — сертификат берётся сам:

```caddyfile
hub.example.com {
    reverse_proxy 127.0.0.1:7717
}
```

nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name hub.example.com;

    ssl_certificate     /etc/letsencrypt/live/hub.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/hub.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:7717;
        proxy_set_header Host              $host;
        # Именно $remote_addr, а НЕ $proxy_add_x_forwarded_for: второй дописывает заголовок,
        # присланный клиентом, и тогда при PARTYCOD_TRUST_PROXY=1 rate-limit обходится
        # подделкой X-Forwarded-For.
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`PARTYCOD_TRUST_PROXY=1` включают **только** вместе с таким прокси. Без него все запросы приходят
с 127.0.0.1, и rate-limit складывает всех участников в одно ведро; с ним, но без перезаписи
заголовка — не защищает вообще.

### 5. Обновление

```bash
sudo systemctl stop partycod
# ... обновить код в /opt/partyco ...
sudo systemctl start partycod
```

регистраций на пять мест, срок жизни, отмена (идемпотентная), `redeem` (идемпотентный и не
понижающий), почта без SMTP и с ним, сокрытие живых кодов от наблюдателя, сокрытие чужих почт в
`GET /v1/members`. Схема (1): миграция 4 — `project_id` nullable, без `DEFAULT`, с внешним ключом,
который база проверяет сама, и с индексом. Приглашения в проект (5): приглашение с проектом ведёт и
на хаб, и в проект, роль в проекте совпадает с ролью приглашения (все три роли, и через регистрацию,
и через `redeem`); приглашение без `projectId` работает по-старому и никого никуда не добавляет —
даже когда проект у зовущего ровно один, и проекта за него не создаётся; позвать можно только в
проект, где ты владелец или мейнтейнер (чужой — `404`, свой-но-участник — `403`, а наблюдателю
отказывают раньше, чем смотрят на проект); погашение атомарно — восемь на пять мест дают пять мест,
пять записей журнала и пять строк в `project_member`, а если строку в проект записать нельзя, то не
записывается вообще ничего (ни участник, ни место, ни повышение роли); тот, кто уже в проекте,
остаётся со своей ролью. Проекты (7): что регистрация проект **не** создаёт и список пуст, создание и
роль владельца у создателя, форма ответа, slug и коллизии slug (включая нелатинское имя),
валидация имени, список — только свои проекты, чужой проект даёт 404, неотличимый от
несуществующего, и на чтение, и на запись, гейт «владелец или мейнтейнер этого проекта» (мейнтейнер
хаба снаружи проекта получает 404, а не 403), роль `owner` раздаёт только владелец, повторное
добавление идемпотентно, а с другой ролью — 409, `PRIMARY KEY` и `CHECK` держат то же самое на
уровне схемы, сокрытие чужих почт в составе проекта (в том числе в своём собственном проекте).

> **Осторожно:** `node --test apps/hub` (каталогом) в Node 24 **не работает как ожидается** —
> позиционный аргумент трактуется как glob, каталог совпадает сам с собой и запускается как файл

> проверив. Указывайте файл или запускайте `node --test` без аргументов из каталога сервиса.

## Чего здесь ещё нет

Честный список, чтобы никто не решил, что оно есть:

- подтверждение почты, восстановление пароля, требования к сложности — отложено владельцем;
- смена пароля и почты, отключение участника через API (колонка `disabled_at` есть и
  учитывается при входе, но ставится пока только руками через SQL). Отсюда следствие, которое
  лучше записать, чем «на всякий случай» закрыть кодом: `POST /v1/projects/members` не смотрит на
  `disabled_at` у того, кого добавляют. Ставить эту колонку нечем, значит и состояния такого в
  системе нет; проверка на него была бы веткой, которую невозможно ни выполнить, ни проверить
  тестом. Появится ручка отключения — проверка появится вместе с ней, в одном шаге;
- **отправка писем.** Приглашения по почте создаются, но письмо не уходит: см. раздел «Почта».
  Ссылку отдаёт UI;
- смена роли после регистрации — кроме одного случая: погашение приглашения повышает роль
  (`POST /v1/invites/redeem`). Понизить роль через API по-прежнему нельзя;
- **приглашения в проект хаб выписывает, но клиент их пока не выписывает.** `projectId` в
  `POST /v1/invites` — необязательное поле, и десктопная панель команды его не шлёт, поэтому
  приглашения оттуда ведут только на хаб, а `peek` у них без `projectName`. Это честно пустое
  состояние, а не поломка: ручка есть, клиент подтянется;
- приглашение по почте **не привязано** к адресу, на который выписано: код — это и есть секрет, и
  вся модель «если SMTP нет, отдай ссылку в руки» построена на том, что её передают. Зарегистрироваться
  по такому коду можно с любого адреса;
- rate-limit переживает рестарт и не распределённый — это `Map` в памяти. Для хаба на 2–10 человек
  он делает то, для чего нужен: гасит онлайновый перебор паролей. От ботнета не спасает и не
  притворяется;
- **у проекта нет ничего, кроме имени и состава.** Ни репозитория, ни trunk-ref'а, ни политики, ни
  архивации — колонка `archived_at` есть, ставить её нечем. Переименовать проект, убрать из него
  человека, сменить ему роль и удалить проект тоже пока нельзя: этих ручек нет, и сообщения об
  ошибках на них не ссылаются;
- **пути с параметром в роутере.** `createRequestListener` сопоставляет `"METHOD /path"` точно,
  поэтому состав проекта — это `?projectId=…`, а не `/v1/projects/:id/members`. Научить роутер
  параметрам — значит переписать и поиск, и таблицу 405, и `Allow` в preflight'е, то есть три вещи,
  на которых стоит каждая существующая ручка, ради более красивого URL;
- остальная схема `hub.db` из §9.1 и всё, что на ней стоит.
